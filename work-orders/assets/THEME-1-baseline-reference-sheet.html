DS2 — shared MUI theme baseline, acceptance & verification sheet (Musterbogen)

The candidate baseline from round 1 is now decided. This sheet is no longer a chooser between variants — it is the acceptance record for the locked createAppTheme(overrides) baseline, and the object later theme changes get re-checked against. The MUI 7.3.11 raw-default comparison stays throughout so the delta is still visible. Every contrast ratio shown is computed by an inline script at render time, not hand-typed. Static HTML/CSS, light mode only, no app code.

Declared coverage

Covers: the full canonical token table above; ink/border/surface tokens including a page-background candidate strip (three near-white values, live contrast checked) and the resulting second muted-ink darkening; the border token split into decorative divider (1.4.11-exempt) and interactive controlBorder (rest/hover/focus/error, all ≥3:1 against both white and the palest page candidate), rendered live on TextField/Select/Checkbox/outlined Button&Chip against MUI's raw default; the 4-tier status semantic split into text/icon and fill+contrastText roles per status, each pairing verified live; the settled typography scale (h1–overline, single scale, no variants); the settled control height (40/44px) and its touch-breakpoint rule; the settled radius pairing (3/8); the binary rest-vs-transient shadow rule; the data-series ramp, its greyscale distinguishability check, and the data-series ramp rendered as a multi-series line chart and grouped bar chart, in colour and desaturated, with no second channel (removed on operator review — see the closing section); a live, render-time WCAG contrast script covering every foreground/background pair the sheet renders; and rendered specimens of Button, TableCell/Table, IconButton, Divider, Tooltip, Select, Checkbox, FormControlLabel, Container, Paper/Card, Chip, TextField/OutlinedInput, Dialog header, and Alert — each against its MUI raw default.

Does not cover: dark mode (explicitly out of scope for v1); components outside the agreed list (DataGrid, Autocomplete, Stepper, Snackbar, Accordion, ToggleButton, etc. — controlBorder is defined as a token and demonstrated on the components above, but not rendered on every component the token could in principle apply to); motion/transition tokens; the actual createAppTheme() implementation or its override API surface; per-app deviations already in production (this is the target baseline, not an audit of the 14 apps against it); the underlying series-4/5 hue proximity itself, which is unchanged by design — the second channel makes it a non-issue for distinguishability rather than removing the near-collision from the ramp; and the operator's final pick among the three page-background candidates, which this sheet proposes but does not decide.

Explicit: the "MUI raw default" column is not a live MUI mount — it is a CSS transcription of MUI v7's documented theme defaults (typography scale, shape.borderRadius: 4, shadows[1]/shadows[2]/shadows[24], palette.text.primary/secondary/disabled, and the Alert standard-variant color mixes). Font: that column substitutes a system-sans stack for Roboto (MUI's actual default) — disclosed here and again at first use, so no reader mistakes it for a font judgment; the comparison that matters is size/weight/radius/color/shadow, not exact glyph shapes.

Font disclosure

The candidate columns throughout this sheet render in DM Sans, weights 400/500/600, embedded as base64 woff2 below (sourced from @fontsource/dm-sans@5.2.8 already vendored in this estate's node_modules — no network fetch). The MUI-default columns render in a system-sans stand-in, not Roboto, because embedding a second full font family solely to color one comparison column wasn't warranted — that substitution is disclosed inline wherever it appears, per the instruction that an undisclosed font swap would invalidate every type judgment made from this sheet.

#FAFAFA is the chosen bg.page — operator decision 2026-08-09, after all three warm candidates read as too warm. The correction: “warmer” against a blue-cast value meant NEUTRAL, not yellow, and the requirement is a lightness step off white to take the glare out, not a hue. #FAFAFA is MUI's own grey[50] and carries no cast. The strip below is kept as provenance of the four-step path: #F5F7F8 (cool, round 1) → #F7F6F3 (far too warm) → #FCFBF9 (still too warm) → #FAFAFA. Three of the six estate apps (hram, fitness-monitor, innoservice) use pure #FFFFFF today and will change visibly on adoption; jg-ferien (#eceae2) and spesix (#EEF4FA) override for identity.

Muted ink re-verified against the new band — and it doesn't clear 4.5:1 anywhere close to white anymore. The badges above use the current tone, #6F777E: 4.549:1 on pure white (barely — 0.049 of headroom over the 4.5 floor) but a failing 4.399 / 4.324 / 4.247 :1 on candidates A / B / C. A value that passes at 4.55 was already fragile; against a near-white page it fails outright. This is the tone now used everywhere ink.muted appears in this document, including the token table below.

Border, split in two: divider vs. controlBorder

WCAG treats these differently, so one token can't serve both roles. divider is a decorative separator or card edge — table rows, dividers, card outline at rest — and is explicitly exempt from 1.4.11 non-text contrast; it stays the pale rgba(33,37,41,0.10) above, unchanged. controlBorder is the visual boundary of an interactive control — the thing a user has to be able to see well enough to know it's a control — and 1.4.11 sets a real floor for it: ≥3:1 against the surface it sits on. The pre-existing token that served this role, input.border (rgba(33,37,41,0.23)), measured on white — it never cleared that floor, flagged and left unfixed in round 2. controlBorder below is derived from the same ink hue (33,37,41), not a new grey, at higher opacity for rest/hover plus the existing primary/critical hues for focus/error — each checked against both white and the palest page candidate (C), since a control can sit on either.

Status, split by role, and the freshness semantic

A single hex can't serve both as text/icon colour and as a fill: #1E8E3E (the old success token) measures 4.20:1 as text on white — and, because the WCAG contrast formula is symmetric, it measures the same 4.20:1 as a fill with white text on top. Failing one direction failed both. Each status below now carries two verified tones: a text/icon tone (≥4.5:1 on white) and a fill tone with its own contrastText (the fill↔contrastText pair itself ≥4.5:1) — plus the existing pale Alert background tint, unchanged, which pairs with the text tone at even higher contrast than pure white gives.

Data-series ramp (categorical, owned by the baseline)

Six series colors, chosen to never overlap the status hues above (no green, no amber/brown, no red, no blue-gray) so a reader never mistakes "series 3" for "success" or "series 6" for "stale." Cool-to-neutral family, muted saturation, kept unchanged this round — the operator's verdict was to keep the six hues and fix distinguishability a different way. The greyscale check below found series 4 (gray 109) and series 5 (gray 106) colliding, with series 2/3/6 clustered in a 10-point band. Fixed this round by encoding series identity in a second, non-colour channel instead of re-hueing anything: distinct stroke-dasharray + marker shape for lines, distinct SVG <pattern> fills for bars/areas. WCAG 1.4.1 requires colour never be the sole carrier of information — a second channel is the structurally correct fix under that criterion, and it resolves the greyscale collision as a side effect rather than needing the hues changed. Each swatch below now carries its series' marker glyph too, so the ramp itself — not just the charts further down — survives desaturation.

Shadow: rest vs. transient — now a binary rule

MUI's shadows[1] (Paper/Card default) is a visible three-layer drop shadow — appropriate for a physical card floating over paper in 2014 Material Design, wrong for a flat 2026 dashboard. Round 1 gave rest state a near-invisible shadow instead of none, which just relocates the judgment call to "how invisible is invisible enough." The decided rule removes the judgment call: Paper and Card at rest have zero shadow, always (elevation: 0, variant: 'outlined' as the default) — border only. Real shadow weight exists only on transient, temporarily-overlaid surfaces: Dialog, Drawer, Menu, Tooltip. This is binary and checkable in a code review — "does this component appear/disappear over other content, yes or no" — instead of a subjective read of a box-shadow value.

✓
The data-series greyscale collision no longer breaks distinguishability, though the underlying hue proximity between series 4 and 5 is untouched by design (operator kept the six colours). The second non-colour channel was removed entirely on operator review (2026-08-09) — bar hatch fills, per-series dash patterns and per-series marker shapes all read as visual noise. Series identity therefore rests on colour (plus position, in grouped bars). Consequence, stated plainly: the series-4/5 greyscale proximity is a live limitation, and a six-series chart distinguished by hue alone does not satisfy WCAG 1.4.1. Resolving that is DS-4's job — direct labelling at the series, or a small luminance stagger — not the theme baseline's, which owns only the colours, demonstrated on a rendered multi-series line chart and grouped bar chart, each shown in colour and desaturated. This is the WCAG-1.4.1-correct fix (colour must never be the sole carrier of information), not a workaround.
