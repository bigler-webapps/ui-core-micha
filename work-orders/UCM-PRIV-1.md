### Shared product contract

- Operator decisions (2026-11-04): use prior opt-in for optional processing uniformly for CH/EU; retain visit measurement only after an explicit choice; use one shared prototype. No consent banner when no optional purposes exist.
- A privacy notice informs; it is not a blanket processing consent or a condition of access. Keep actual terms acceptance, study consent, AI disclosure/release and browser push/geolocation permissions separate.
- The deployment's actual controller, app/site, origins, languages, document versions and services define the scope. Do not assume bigler-consult is controller for a client-operated app or copy consent across apps/subdomains.
- Unknown, missing, expired, malformed or unavailable choice means optional processing is off. A recorded legacy boolean/cookie never counts as a purpose-specific opt-in.
- An explicit requested operation may use the storage actually necessary for it, with a documented justification and lifetime. Being local, first-party, cookieless, server-side or labelled "functional" does not by itself establish necessity.
- No optional request, SDK initialisation, iframe, beacon, identifier creation/read, prefetch or queued event replay before a valid choice. Revocation blocks new work immediately and clears only storage owned by the withdrawn purpose.
- Do not delete research files, customer drafts, tickets, carts, reaction ownership, account sessions or other essential functional data through a generic cookie-clear operation. Existing server records are governed separately; withdrawal does not falsely promise to undo past transmissions.
- Roll out on existing deployment/trunk conventions. Runtime/edge behavior and uploaded legal texts were not verified by the source inventory; each app needs bounded evidence on its actual routes before claiming complete coverage.

### Scope boundaries

No server/secret/provider-console change, production promotion, framework migration, new analytics vendor or broad dependency refresh is included. Narrow shared-library adoption pins and necessary lock/migration changes are in scope. Other active work must remain intact.

### UI and service lifecycle

- A nonblocking first-choice surface appears only when configured optional purposes need a decision. "Necessary only" and "Allow all" have equal prominence on its first layer, plus settings. Closing/continuing navigation does not grant anything. No preselected optional purpose.
- Settings remain reachable without login from the public footer and inside the account area. Show separate purposes, actual provider/storage duration details and current selections. Necessary functions are information, not a misleading disabled consent checkbox.
- A provider initialises before optional imports/effects. All optional service entry points use a purpose-aware lifecycle guard, including dynamic imports, requests, iframes, storage reads/writes and callback races. App code owns the actual providers; the shared package does not load vendors speculatively.
- A positive server-confirmed choice activates only matching services. Refusal/revocation stops scheduling immediately, tears down active integrations where possible, blocks late callbacks and clears registered purpose-owned keys/cookies/caches. Never run localStorage.clear() or delete all IndexedDB databases/caches.
- Synchronise choices between tabs on the same supported scope without letting stale optimistic updates resurrect grants. Do not auto-enable choices at login/logout, account switch or on a new device.
- Support storage-disabled/private/offline conditions: necessary app use remains possible; optional processing stays off if a durable grant cannot be established. Give an honest retry state. Persisting a refusal must not require registration.
- Empty optional configuration shows notice information/settings as appropriate, without a banner or acceptance fiction. Use the actual controller and configured document locale; preserve supported app languages, including DE/EN/FR variants and existing regional language choices.
- Provide explicitly adopted replacements for CookieConsentStep and profile statement controls. Retain legacy exports only during rollout, deprecate them and remove under UCM-PRIV-2. Keep name completion, actual terms acceptance, AI permissions and browser permissions intact.

### Released backend contract this UI builds against (django-core-micha 3.22.0, module `django_core_micha.privacy`)

Mounted by the host at an `apiBase` (default `/api/privacy/`; make it configurable like `createTermsApi` in `src/auth/termsApi.js`). Every response is JSON, `Cache-Control: no-store`. Errors look like `{code, retryable, state?}`.

- `GET {apiBase}manifest/` -> `{app, site, locales, controller:{name,contact}, notice:{version, documents:{<docId>:{<locale>:<reference>}}}, choice_validity_days, purposes:[{id, revision, required, justification?, label:{<locale>:str}, summary:{<locale>:str}, services:[{id, provider, trigger, data_categories, recipients, transfers, browser_storage:[{kind:"cookie|localStorage|sessionStorage|indexedDB|none", name, scope, lifetime}], server_retention}], withdrawal_clears:[storage names]}], necessary_storage:[...same storage shape...], config_version}`. 404 `not_configured` = the host has not adopted the module: render NOTHING (no banner, no settings link).
- `GET {apiBase}choices/` -> `{receipt_state:"unset|present", seq, config_version, notice_version, choices:{<purposeId>:{state:"granted|refused|unset", revision, expires_at}}}`; only OPTIONAL purposes are listed. Creates nothing, sets no cookie.
- `POST {apiBase}choices/` body (exactly these keys): `request_id` (uuid string; `crypto.randomUUID()` with a fallback), `expected_seq` (the `seq` of the last state you hold), `notice_version`, `config_version`, `locale` (one of manifest.locales; map the i18n language, fall back to the first), `channel` (`banner|settings|other`), `choices` (`{purposeId: "granted"|"refused"}`, optional purposes only). Success 200 returns the same shape as GET and sets the signed host-only receipt cookie (you never read or write it; HttpOnly). Errors: 409 `stale` (a grant lost against a newer state; `state` is the fresh state), 409 `stale_notice` / `stale_config` (`state` fresh; the client must re-read and the user must decide again), 422 `unknown_purpose`, 429 `throttled` (retryable), 503 `unavailable` (retryable, nothing stored), 403 `csrf_failed|origin_not_allowed`, 413/400 invalid. A REFUSAL write is always applied by the server regardless of `expected_seq`; a GRANT needs `expected_seq === seq`.
- CSRF: the POST is CSRF protected. The shared `src/auth/apiClient.jsx` axios instance already sends `X-CSRFToken` from the `csrftoken` cookie; prime the cookie first with a GET to `CSRF_URL` (`src/auth/authConfig.jsx`, `/api/csrf/`) before the first write, deduplicated like `primeDeclarationCsrf` in `src/billing/DeclarationForm.jsx:36-56`.
- Server truth: choices are valid 180 days for grant AND refusal, are per browser + site, and are never account-linked. The UI must not store choices in localStorage/sessionStorage/cookies itself and must treat the server state as the only source of grants.

### Decisions (binding)

New opt-in module `src/privacy/` (nothing is mounted by default; adoption is explicit):

- `src/privacy/privacyApi.js`: `createPrivacyApi(overrides, {apiBase, csrfUrl})` + `defaultPrivacyApi` (`getManifest`, `getChoices`, `saveChoices(body)`, `primeCsrf`), same override pattern as `createTermsApi`.
- `src/privacy/PrivacyProvider.jsx` exporting `PrivacyProvider` and `usePrivacy()`: loads manifest + choices; value `{status:"loading|ready|unconfigured|error", manifest, choices, needsDecision, saveState:"idle|saving|saved|error", error, hasGrant(purposeId, serviceId?), save(choices, channel), acceptAll(channel), necessaryOnly(channel), retry(), settingsOpen, openSettings(), closeSettings()}`. `needsDecision` = at least one optional purpose is `unset`. No optional purposes (empty list) or `unconfigured` => never needsDecision. `error`/`loading` => all optional purposes OFF.
- **Lifecycle guard** `src/privacy/serviceRegistry.js` (exported): `registerPrivacyService({purposeId, serviceId, activate, deactivate, ownedStorage:{cookies:[names], localStorage:[keys], sessionStorage:[keys], caches:[names], indexedDB:[names]}})` returns an unregister function; `useGrantedPurpose(purposeId, serviceId?)` hook -> boolean; `guardedImport(purposeId, loader, serviceId?)` (resolves only while granted; rejects/never calls `loader` otherwise); `createPrivacyGuard(purposeId)` returning `{isCurrent(), run(fn)}` where a generation counter makes callbacks started under a grant a no-op after revocation (late-callback race). A grant (server-confirmed by a successful POST or by a fresh GET) calls `activate` of matching registered services ONLY; refusal/revocation immediately (before the network call returns) stops scheduling, calls `deactivate`, bumps the generation and removes ONLY the `ownedStorage` entries of the withdrawn purpose (exact names, never `localStorage.clear()`, never enumerate-and-delete databases/caches beyond the registered names). Shared package never imports a vendor.
- **Cross-tab:** `BroadcastChannel` (fallback `storage` event on a throwaway key) used ONLY as a "state changed, re-read" signal; a received message triggers a `GET` and never carries grants. A POST is serialised across tabs with the Web Locks API (`navigator.locks.request`) when available (this is the documented client duty for the first-write race: re-read state inside the lock and use the fresh `seq`). Optimistic UI never shows a grant before the server confirmed it. A refusal updates local state immediately and is then sent; if the send fails the UI shows the honest retry state with services still OFF (never claims persistence).
